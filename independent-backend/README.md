# MANO independent backend — synthetic staging only

This isolated Node 24 / PostgreSQL 18 service is NOT wired into the existing public Express app, Android client or Firebase. It binds loopback port 3100, starts only with MANO_INDEPENDENT_STAGE_ENABLED=true and a random stage gate, and permits synthetic aliases only. No live patient information, Firebase credentials, deployment or clinical AI. The root package and existing UI remain unchanged.

## API / authorization
Requests require x-mano-stage-token and Authorization: Bearer (random 32-byte base64url session secret). Database stores SHA-256 digest, expiry, revocation, account status. Test accounts are provisioned by the operator/CI, not publicly registered. Never log tokens. The service cannot create roles, accounts or sessions. Parent POST /v1/profiles accepts only demo alias and integer ageMonths. GET /v1/profiles returns own profiles for parents, only consented profiles in active pharmacies with active membership for pharmacists. POST /v1/profiles/:id/shares requires owner and explicit synthetic-v1 consent with pharmacyId. DELETE /v1/profiles/:id/shares/:pharmacyId revokes. No clinical advice, file storage, prescriptions, cross-tenant search or public login. All SQL is parameterized; no CORS; bounded input and no-store responses. Role/consent changes affect subsequent requests; in-flight revocation linearization still needs further work before real data. RLS is an additional defense against missing query filters, not against arbitrary compromise of a trusted application process.

## Migration plan (non-writing)
Current Firestore rules expose owner-scoped profiles, doseLogs, consultations, bookmarks, feverLogs, visitDrafts, vaccineRecords and syrupScans. migration-plan.mjs maps aggregate synthetic counts only; it performs zero writes. Firebase Functions separately hold authoritative consultation cases, pharmacy registry, staff access, triage passes, retention and deletion state; inventory actual collections and Storage with authorized read-only credentials before mapping. Preserve original IDs, event times, source provenance and consent versions; never import old direct consultation docs as authoritative. Stage new accounts with reviewed owner mapping and verified identity, not email/phone matching alone; never import raw credentials or infer staff role from client data. Build a dry-run with counts, orphan detection, hashes, reconciliation and quarantine; then test idempotent import in a separate encrypted staging store. Decide retention/deletion and rollback before any cutover; do not delete Firebase or copy real data now. No patient migration implemented in this phase.

## Phase 2 additions
The synthetic database now enforces RLS on profiles and shares, using a transaction-local session digest and narrowly scoped SECURITY DEFINER helpers. Direct access to account/session/membership tables is revoked from runtime. The helpers rely on the trusted runtime and migration owner; independent security review and concurrency testing remain necessary. The optional demo-auth module exercises HMAC-bound single-use OTPs, persistent per-handle cooldown, attempt limit, expiry and session issuance against pre-enrolled synthetic accounts. It has no public route or SMS provider. Logout revokes the current session. AES-256-GCM backup helpers cover synthetic profiles only, not actual PostgreSQL backups. Neither real authentication nor real data use is approved.

## Internal operator verification
After the schema is installed in a dedicated synthetic database, run node preflight.mjs with only server-side MANO_STAGE_DATABASE_URL and the explicit transport policy. The script checks database/role names, non-privileged role, RLS, session and audit read restrictions; no writes or connection secrets. It is not proof of full privilege isolation. A real-data rollout requires a reviewed provider, separate migration and runtime credentials, strong transport, real backup restore, deletion policy, access/clinical review and cutover authorization. reconcile.mjs performs a synthetic profile dry run with explicit owner mapping, duplicate quarantine, hashes, target conflict detection and zero writes.
