# MANO independent backend — synthetic staging only

This isolated Node 24 / PostgreSQL 18 service is NOT wired into the existing public Express app, Android client or Firebase. It binds loopback port 3100, starts only with MANO_INDEPENDENT_STAGE_ENABLED=true and a random stage gate, and permits synthetic aliases only. No live patient information, Firebase credentials, deployment or clinical AI. The root package and existing UI remain unchanged.

## Liara setup (future internal test, not production)
1. Rotate any previously exposed PostgreSQL administrator password. Never send secrets to chat or GitHub.
2. Confirm both services are on my-network. Keep public DB access disabled. In PostgreSQL create a NEW empty database mano_stage, and separate non-owner LOGIN role mano_stage_app; grant CONNECT to mano_stage only, with no superuser, CREATEDB, CREATEROLE or membership in other privileged roles. Ensure ownership and other inherited grants are reviewed. Use an administrative migration role to apply schema.sql exactly once to that dedicated database. Never run on postgres or a patient database. Review managed-service role/CONNECT permissions and TLS first.
3. Store only the runtime role connection URI in server-side secret MANO_STAGE_DATABASE_URL (example with placeholder: postgresql://mano_stage_app:REPLACE@mano-db:5432/mano_stage). Percent-encode passwords when forming the URI. Never use VITE_ or root credentials.
4. MANO_STAGE_DB_TLS=verify-full with provider CA in MANO_STAGE_DB_CA if required; verify server certificate hostname. If private network TLS is unavailable, private-test is allowed only for synthetic staging and known private/local hosts; no real data.
5. Generate independent random stage access token with node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))". Store as MANO_STAGE_ACCESS_TOKEN on server only. Do not add to browser bundle. Leave MANO_INDEPENDENT_STAGE_ENABLED=false outside controlled test execution. This extra token is a test perimeter, not identity.
6. Install dependencies within independent-backend; generate/review/commit the dedicated lockfile before a release, then use npm ci. Current CI generates a candidate lockfile artifact because local registry access was unavailable. Run unit, migration and real PostgreSQL integration tests. Existing Liara deployment is not changed and must NOT be pointed at this branch for public use.

## API / authorization
Requests require x-mano-stage-token and Authorization: Bearer (random 32-byte base64url session secret). Database stores SHA-256 digest, expiry, revocation, account status. Test accounts are provisioned by the operator/CI, not publicly registered. Never log tokens. The service cannot create roles, accounts or sessions. Parent POST /v1/profiles accepts only demo alias and integer ageMonths. GET /v1/profiles returns own profiles for parents, only consented profiles in active pharmacies with active membership for pharmacists. POST /v1/profiles/:id/shares requires owner and explicit synthetic-v1 consent with pharmacyId. DELETE /v1/profiles/:id/shares/:pharmacyId revokes. No clinical advice, file storage, prescriptions, cross-tenant search or public login. All SQL is parameterized; no CORS; bounded input and no-store responses. Role/consent changes affect subsequent requests; in-flight revocation linearization and DB row-level security need further work before real data. Shared app-role access to tables is not equivalent to tenant-level database isolation.

## Migration plan (non-writing)
Current Firestore rules expose owner-scoped profiles, doseLogs, consultations, bookmarks, feverLogs, visitDrafts, vaccineRecords and syrupScans. migration-plan.mjs maps aggregate synthetic counts only; it performs zero writes. Firebase Functions separately hold authoritative consultation cases, pharmacy registry, staff access, triage passes, retention and deletion state; inventory actual collections and Storage with authorized read-only credentials before mapping. Preserve original IDs, event times, source provenance and consent versions; never import old direct consultation docs as authoritative. Stage new accounts with reviewed owner mapping and verified identity, not email/phone matching alone; never import raw credentials or infer staff role from client data. Build a dry-run with counts, orphan detection, hashes, reconciliation and quarantine; then test idempotent import in a separate encrypted staging store. Decide retention/deletion and rollback before any cutover; do not delete Firebase or copy real data now. No patient migration implemented in this phase.
