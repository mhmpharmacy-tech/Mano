# مانو وب: ساخت، بررسی آزمایشی و بازگشت نسخه

این راهنما برای نسخهٔ وب React است. اجرای فرمان‌های ساخت یا آزمون، مجوز انتشار بالینی نیست. هیچ استقرار، تغییر دامنه، فعال‌سازی AI یا حذف دادهٔ واقعی در این مرحله انجام نشده است. دادهٔ بررسی باید ساختگی باشد.

## دو مسیر اجرای مشخص

| مسیر | ورودی | محدودیت |
|---|---|---|
| سرور Node/Express | `dist/`، API سلامت و آمادگی، درگاه سروریِ حفاظت‌شده | روی Node 22 یا جدیدتر، پشت HTTPS و پراکسی مورد اعتماد اجرا شود. توکن درگاه فقط برای فراخوان سروری است. |
| Firebase Hosting مستقل وب | `firebase.web.json` → `dist/` | فقط فایل ثابت؛ مسیرهای `/api/*` به HTML یا Cloud Function دیگری بازنویسی نمی‌شوند. `/api/health` در این مسیر وجود ندارد. |

`firebase.json` موجود برای Android، Firestore و Functions دست‌نخورده باقی می‌ماند. برای انتشار وب از تنظیم مستقل استفاده کنید تا انتخاب اشتباهِ ریشهٔ `public/`، صفحهٔ React را حذف نکند و یک استقرار وب، backend را نیز تغییر ندهد.

مسیرهای ساخته‌شده عبارت‌اند از `/` برای React، `/preview/` برای طرح پیشین، `/care/` و `/pharmacist/` برای ورودی‌های موجود. ناوبری React از hash استفاده می‌کند؛ نشانی ناشناخته یا فایل JS گم‌شده نباید پاسخ ۲۰۰ HTML بگیرد. پارامتر `?pharmacy=...` در تغییر مسیر پوشهٔ داروساز حفظ می‌شود.

## بررسی نسخهٔ نامزد

از checkout تمیزِ شناسهٔ همان نسخه و Node 22 استفاده کنید:

```bash
npm ci
npm run check
npm run build
npx tsx scripts/verify-web-build.ts
npx playwright install --with-deps chromium
npm run test:browser
```

اسکریپت بررسی، وجود چهار ورودی و دارایی‌های محلیِ ارجاع‌شده را بررسی می‌کند. همچنین اگر مقدار متغیرهای سروری `GEMINI_API_KEY` یا `MANO_GATEWAY_ACCESS_TOKEN` در محیطِ همان فرمان موجود باشد، نبود آن مقدارها در فایل‌های متنِ خروجی را می‌آزماید؛ این بررسی، اسکن جامع همهٔ انواع رازها نیست. نام یا مقدار راز در گزارش خطا چاپ نمی‌شود. اسکریپت چیزی منتشر نمی‌کند.

نتیجهٔ CI، شناسهٔ commit، نسخهٔ Node، خروجی ساخت و آزمون مرورگر را برای همان نامزد نگه دارید. `dist/` متعلق به همان ساخت را با checksum بایگانی کنید؛ فایل‌های `.env`، اطلاعات بیمار و کلیدها را داخل آرشیو عمومی قرار ندهید. آزمون روی گوشی و صفحه‌خوان واقعی، بررسی چند مرورگر و تأیید بالینی، جداگانه لازم‌اند.

## اجرای آزمایشی Express

متغیرهای محیطی را خارج از مخزن و فقط در فرایندِ سرور تأمین کنید. پیش‌فرض زیر باید تا تکمیل مستقل شرایط فعال‌سازی باقی بماند:

```text
NODE_ENV=production
MANO_CLINICAL_SERVICE_ENABLED=false
```

```bash
NODE_ENV=production PORT=3000 npm start
```

`/api/health` باید پاسخ ۲۰۰، بدون راز و بدون اطلاعات کودک بدهد؛ در پیش‌نمایش، سرویس بالینی غیرفعال است. `/api/ready` هنگام پذیرش کار ۲۰۰ و هنگام تخلیهٔ فرایند ۵۰۳ می‌دهد. تعادل بار باید از آمادگی استفاده کند؛ سلامت فرایند به معنی آماده بودن خدمات بالینی نیست.

در SIGTERM/SIGINT، فرایند درخواست تازه نمی‌پذیرد و درخواست‌های موجود حداکثر ۱۰ ثانیه فرصت پایان دارند؛ سپس اتصال باقی‌مانده بسته و خروج اجباری با کد ۱ مشخص می‌شود. مهلت خاتمهٔ سرویس اجراکننده را بیشتر از این زمان قرار دهید. توقف یک درخواست جاری، جای تکرار بی‌خطرِ عملیات در backend را نمی‌گیرد.

TLS، دامنه، گواهی، HSTS، تنظیم واقعی پراکسی، فایروال و خط‌مشی گزارش خطا باید در محیط آزمایشی تأیید شوند. کد عمداً به `X-Forwarded-For` دلخواه اعتماد نمی‌کند. بدنهٔ درخواست بالینی، توکن یا محتوای پشتیبان را در access log یا ابزار گزارش خطا ثبت نکنید. AI Gateway حافظه‌ای Express، سهمیه یا audit مشترک چند نمونهٔ سرور ارائه نمی‌کند؛ سرویس واقعیِ کاربران باید از مسیر احرازشده و بررسی‌شدهٔ backend استفاده کند.

## Firebase Hosting وب

`firebase.web.json` پیش‌نمایش محلی را منتشر می‌کند و backend یا قواعد Firestore را همراهش deploy نمی‌کند. فرمان‌های زیر نمونهٔ آماده‌سازی‌اند؛ مقدار پروژهٔ آزمایشی باید مشخص شود و خودِ deployment نیازمند تصمیم انتشار مالک پروژه است:

```bash
npx tsx scripts/generate-web-hosting-config.ts --out=firebase.web.generated.json
```

مولد فقط تنظیمات می‌نویسد و چیزی deploy نمی‌کند. با `VITE_MANO_ONLINE_ENABLED=false`، CSP صفحهٔ اصلی فقط اتصال هم‌مبدأ را می‌پذیرد. برای ساخت آنلاینِ بررسی‌شده، متغیرهای عمومی `VITE_FIREBASE_PROJECT_ID`، `VITE_FIREBASE_AUTH_DOMAIN` و `VITE_FIREBASE_FUNCTIONS_REGION` را همراه پرچم فعال‌سازی، با مقادیر همان build وارد محیط فرمان کنید؛ CSP فقط مبدأ دقیق Auth و Function همان پروژه و مسیرهای مشخص Google/reCAPTCHA را اضافه می‌کند. مقدار نامعتبر خطا می‌دهد. متغیرهای سروری را با پیشوند `VITE_` قرار ندهید.

در Express نیز همین شناسه‌های عمومیِ build را به محیط اجرای سرور بدهید تا CSP سرور با پیکربندی مرورگر هم‌خوان باشد. دامنهٔ Auth باید در Firebase برای همان محیط مجاز شده و App Check در backend واقعاً enforce شده باشد. CSP صحیح، به‌تنهایی احراز هویت یا رضایت کاربر ایجاد نمی‌کند. عملکرد واقعی popup و reCAPTCHA با دامنه و site key واقعی باید در staging آزمایش شود.

پس از انتخاب پروژه، فرمان بررسیِ کانال آزمایشی چنین شکلی دارد؛ این فرمان در این مرحله اجرا نشده است:

```bash
firebase hosting:channel:deploy mano-web-review --config firebase.web.generated.json --project YOUR_STAGING_PROJECT --expires 7d
```

در کانال آزمایشی، `/`، `/preview/`، `/care/`، `/pharmacist/?pharmacy=sample_123`، فایل‌های محلی و ۴۰۴ مسیر API ناشناخته را بررسی کنید. در حالت ثابت، انتظار API Express نداشته باشید. پاسخ‌های HTML و API در Express `no-store` هستند؛ فقط JS/CSS دارای hash محتوایی، cache تغییرناپذیر می‌گیرند. این هدرها، اطلاعاتی را که خود کاربر در `localStorage` یا فایل پشتیبان ذخیره کرده پاک نمی‌کنند.

فایل Android App Links در مخزن هنوز fingerprint نمونه دارد. تنظیم مستقل Firebase وب، `.well-known/**` را عمداً منتشر نمی‌کند و Express نیز فایل نقطه‌دار را عمومی نمی‌کند. پس از دریافت fingerprint واقعیِ امضای release/Play، پیکربندی انتشار App Links باید جداگانه تأیید و روی دستگاه واقعی آزمایش شود؛ قبل از آن هیچ ادعای پیوند تأییدشده یا توزیع عمومی QR مجاز نیست.

## بازگشت به نسخهٔ قبل

نسخهٔ قبلی باید پیش از rollout، همراه با commit و artifact مشخص موجود باشد. اگر آمادگی، بارگذاری ورودی‌ها، آزمون رفتار یا بررسی خطا شکست خورد:

1. ترافیک تازه را از نامزد خارج و flag سرویس بالینی را خاموش نگه دارید.
2. همان artifact قبلی و تنظیمات محیطیِ متناظر را در staging اجرا کنید؛ build تازهٔ شناسه‌ای مبهم را جایگزین artifact تأییدشده نکنید.
3. سلامت، آمادگی و مسیرهای اصلی را بررسی، سپس ترافیک را طبق روش اجراکننده برگردانید. در Hosting، release قبلیِ همان site را از ابزار رسمی Hosting بازیابی و نتیجه را بررسی کنید.
4. مهاجرت یا حذف داده را معکوس فرض نکنید. بازگشت فایل‌های وب، دادهٔ محلی مرورگر، نسخه‌های پشتیبان یا تغییر backend را به وضعیت قبل برنمی‌گرداند. ناسازگاری schema باید با نسخهٔ داده و آزمون بازیابی مدیریت شود.

این مراحل در محیط production اجرا یا تأیید نشده‌اند؛ این سند و آزمون‌های کد، جای شواهد عملیِ staging و تأیید انتشار را نمی‌گیرند.
